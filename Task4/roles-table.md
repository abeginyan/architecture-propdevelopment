# Задание 4. Ролевая модель доступа к Kubernetes (PropDevelopment)

## 1. Как устроен доступ

- **Пространства имён по доменам** (оргструктура компании): `sales` (Продажи), `housing` (ЖКУ), `finance` (Финансы), `data` (Дата), `smart-home` (новые сервисы «Умный дом» из Задания 3; принадлежат домену ЖКУ).
- **Права выдаются группам, не людям.** Человек получает сертификат, в котором указаны его группы. Перешёл в другую команду — меняется группа, а роли остаются прежними.
- **Привилегированные действия** (чтение секретов, вход в работающий под) есть только у ролей `pd-ops-engineer` и `pd-security-auditor`.
- **Права доступа (RBAC) никто, кроме администратора кластера, не меняет.** DevOps может только смотреть их. Это закрывает проблему из ТЗ: ИБ-специалист получает информацию об изменениях, потому что изменения прав идут через него.

## 2. Таблица ролей (по шаблону)

| Роль | Права роли | Группы пользователей |
| --- | --- | --- |
| `pd-viewer` (ClusterRole, выдаётся RoleBinding в пространстве имён домена) | Только чтение (get, list, watch): поды, логи подов, сервисы, endpoints, configmaps, тома, serviceaccounts, квоты, события, deployments, statefulsets, daemonsets, replicasets, jobs, cronjobs, ingresses, networkpolicies, HPA. **Секреты не читает.** Изменять ничего нельзя | `sales-viewers`, `housing-viewers`, `finance-viewers`, `data-viewers`: владельцы продуктов, бизнес-аналитики, операционная команда (менеджеры) |
| `pd-developer` (ClusterRole, RoleBinding в пространстве имён домена) | Всё из `pd-viewer` + создание, изменение, удаление deployments, statefulsets, services, configmaps, томов, jobs, cronjobs, ingresses, HPA; удаление подов (перезапуск). **Нельзя:** секреты, сетевые политики, права доступа | `sales-developers`, `housing-developers`, `finance-developers`, `data-developers`: разработчики функциональных команд |
| `pd-ops-engineer` (ClusterRole, RoleBinding в пространстве имён домена). **Привилегированная** | Просмотр как у `pd-viewer` + перезапуск подов, изменение и масштабирование deployments и statefulsets, **чтение секретов**, **вход в под (pods/exec)** и проброс порта. Создавать и удалять приложения не может | `sales-ops`, `housing-ops`, `finance-ops`, `data-ops`: инженеры по эксплуатации |
| `pd-cluster-configurator` (ClusterRole, ClusterRoleBinding на весь кластер) | Полное управление пространствами имён, квотами, лимитами, томами, хранилищами, ingress, сетевыми политиками, CRD, рабочими нагрузками (apps, batch, autoscaling); узлы: просмотр и cordon/drain. Секреты: только создание, замена и удаление, **без чтения**. RBAC (roles, bindings): **только просмотр** | `platform-devops`: DevOps-инженеры |
| `pd-security-auditor` (ClusterRole, ClusterRoleBinding на весь кластер). **Привилегированная** | Только чтение (get, list, watch) всех ресурсов кластера, включая секреты, RBAC и события. Ничего изменить, удалить или запустить нельзя | `security-auditors`: специалист по ИБ |

Требование задания выполнено так: привилегированные группы — `*-ops` и `security-auditors`; группа «только просмотр» — `*-viewers`; группа, которая «настраивает кластер», — `platform-devops`. Дополнительно есть `*-developers`.

## 3. Какая команда в какой группе

| Участник из ТЗ | Группа | Роль |
|---|---|---|
| Владелец продукта | `<домен>-viewers` | `pd-viewer` |
| Бизнес-аналитик | `<домен>-viewers` | `pd-viewer` |
| Менеджер операционной команды | `<домен>-viewers` | `pd-viewer` |
| Разработчик | `<домен>-developers` | `pd-developer` |

| DevOps-инженер | `platform-devops` | `pd-cluster-configurator` |

## 6. Связь с рисками аудита (Задания 1–3)

- Данные одного клиента видны другому, нет ограничений на доступ: доступ разделён по доменам и ролям, секреты закрыты от разработчиков и наблюдателей.
- ИБ не получает информацию об изменениях: права меняет только администратор, ИБ имеет полное чтение для проверки.
- Утечка секретов (например, ключей интеграции с партнёром «Умный дом»): чтение секретов только у `ops` и ИБ, а DevOps может их менять, но не читать.

## 7. Что не вошло и стоит добавить в промышленной среде

- Вход людей через корпоративный каталог (Keycloak/Active Directory, OIDC) вместо сертификатов. Сертификаты выбраны, потому что работают в пустом Minikube без внешних систем.
- Срок жизни сертификатов 30 суток; отозвать сертификат досрочно в Kubernetes нельзя, поэтому для реальных пользователей нужен OIDC с короткоживущими токенами.
- Аудит-журнал API-сервера, NetworkPolicy, Pod Security Admission, ограничение экстренного доступа (break-glass) с cluster-admin.
